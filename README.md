# 人工衛星開発への道（Road to Satellite Development）

人工衛星の開発に初めて取り組む大学生が、必要な技術の全体像と、それぞれの学び方を見つけるためのページです。

> **モックアップ（MVP）です。** 本はすべて調べて挙げた「候補」（`candidate: true`）で、チームではまだ決めていません。

## 1. このページでできること

- **本のロードマップ**が主役。行＝分野、列＝入門・基礎・専門に本を並べ、「この本の次に読む本」を矢印で表す
- **スキルは本の補足として控えめに**出す
  - 本のカードの下に「身につく：○○・△△」と小さな文字で、その本で身につくスキルを出す
  - まだ本が決まっていないスキルは、各分野の行の下に「本を募集中のスキル」として小さくまとめる
  - スキル名を押すと、詳細（概要・目的・前提・学ぶ内容・ツール・実践課題・到達基準）が出る
- 分野は**共通基礎＋9分野**（電源・熱・構造・C&DH・通信・姿勢制御・システム・宇宙工学・製造試験）
  - システム（システムズエンジニアリング）は独立した分野であり、ほかの8分野を横断的につなぐ役割も持つ
- 本を選ぶと、書誌情報・前後に読む本・身につくスキルが出て、つながる矢印が光る
- 分野カードを押すと、その分野と共通（全体像）の本だけを表示する
- 本に「読んだ」、スキルに「身についた」のチェックを付けられる。分野ごと・全体の進捗が出る
  - チェックは**そのブラウザの中（localStorage）にだけ保存**される。登録は不要。ほかの人には見えない
- 下部の「最終目標」で、各分野が衛星開発のどの工程（ミッション定義〜運用）につながるかを示す

スキルの前提（`nodes.yaml` の `prerequisites`）の順番は、大学の工学系学類の授業の履修順（力学→材料力学→振動工学、
熱力学→伝熱工学、電気回路→電子回路→パワーエレクトロニクス、フィードバック制御→線形システム制御 など）を参考にしています。
画面ではスキルの詳細の「必要な前提知識」「次に進めるスキル」に出ます。

## 2. ファイルの構成

```
satellite-learning-roadmap/
├─ index.html          … 画面の骨組み
├─ style.css           … 見た目（ライトモード。本の目録のように罫線で区切る。ヘッダーはネイビー、スマホ対応）
├─ app.js              … 動き（データの読み込み・表と矢印の描画・詳細・チェックの保存）
├─ data/               … ★中身はここだけ直せばよい
│  ├─ tracks.yaml      … 分野（名前・色・説明）
│  ├─ nodes.yaml       … スキル（本のカードの「身につく」・詳細に出る）
│  ├─ books.yaml       … 本・資料と読む順（本のロードマップの本体）
│  ├─ process.yaml     … 最終目標の工程図
│  └─ progress.json    … 旧モックアップのチーム進捗用（今は使っていない。チーム進捗を作るときに使う予定）
├─ tools/
│  ├─ validate_data.py … data/ の矛盾を見つける検査スクリプト
│  └─ make_book_survey.py … 分野ごとの「どの本が必要か」質問票（Markdown）を作るスクリプト
└─ .github/
   ├─ workflows/deploy-pages.yml           … GitHub Pages への自動デプロイ
   └─ ISSUE_TEMPLATE/book-recommendation.yml … 本の推薦フォーム（Issue フォーム）
```

- **ビルドの手順はありません**（npm などは不要）。ファイルを置くだけで動きます
- 外部ライブラリは [js-yaml](https://github.com/nodeca/js-yaml)（YAML を読む）だけで、CDN から読み込みます
- パスはすべて相対パス（`./data/...`）なので、GitHub Pages のサブパス（`https://ユーザー名.github.io/リポジトリ名/`）でもそのまま動きます

## 3. 手元で開く方法

データファイルを読み込むため、`index.html` をダブルクリックで開くだけでは動きません（ブラウザの安全のための制限）。
簡単なサーバーを立ててから開きます。

```
cd satellite-learning-roadmap
py -m http.server 8765
```

ブラウザで http://127.0.0.1:8765/ を開きます。止めるときはターミナルで `Ctrl + C`。
ファイルを直したのに表示が変わらないときは、`Ctrl + Shift + R`（強制再読み込み）を押してください。

## 4. 中身の直し方

### スキルを足す（`data/nodes.yaml`）

```yaml
- id: eps-power-budget        # 英小文字とハイフン。チェックの保存に使うので後から変えない
  title: 電力収支の計算
  field: eps                  # tracks.yaml の id
  stage: applied              # basic（基礎）/ applied（応用）/ practice（実践）
  prerequisites: [eps-components, space-orbit-basics]   # 先に身につけるスキル（矢印になる）
  summary: 1周回の発電量と消費電力を比べ、電気が足りるかを計算する
  purpose: 運用モードごとに、電気が足りるかを設計の段階で確かめる
  learn: [日照率と軌道の関係, 機器ごとの消費電力]
  tools: [Excel, Python]
  exercise: 機器リストと軌道から、電力収支表を作る
  goal: [運用モードごとの電力収支表を作れる]       # 「〜できる」の形で書く
  books: [patel]              # books.yaml の id。空 [] なら「募集中」と出る
  events: [電源系 勉強会]      # 関連する勉強会（任意）
```

### 本を足す（`data/books.yaml`）

```yaml
- id: patel
  title: Spacecraft Power Systems（2nd ed.）
  author: Mukund R. Patel・Omid Beik
  publisher: CRC Press
  year: 2024
  url: "https://..."          # 出版社のページ。なければ CiNii の検索結果
  field: eps
  level: advanced             # intro（入門）/ basic（基礎）/ advanced（専門）
  lang: en                    # ja / en
  next: []                    # 次に読む本の id（矢印になる）
  note: ひとこと
  candidate: true             # チームで確定したら消す
```

**本を載せるときのルール**：実在を CiNii（https://ci.nii.ac.jp/books/ ）か出版社のページで確かめ、そのページの URL を書く。架空の本や確かめていない URL は載せない。

### 本の推薦を受け付ける（Issue フォーム）

メンバーは YAML を直さなくても、ページから本を推薦できます。

1. ページの各分野の下の「＋ ○○の本を推薦する」、またはスキルの詳細の「＋ このスキルの本を推薦する」を押す
2. GitHub の推薦フォームが、分野（とスキル）が入った状態で開く。書名・レベル・理由を書いて送信する
   （GitHub のアカウントがあれば、リポジトリの権限がなくても送れます）
3. 管理者が Issue を見て、実在を確かめてから `data/books.yaml`（と `nodes.yaml` の `books`）に追加し、Issue を閉じる

**使い始めるときの設定**（GitHub に公開したあと1回だけ）

- `app.js` の上のほうにある `GITHUB_REPO_URL` に、リポジトリのアドレスを入れる。空のあいだはリンクが「公開後に使えます」と表示され、押せません
- リポジトリの **Issues → Labels** で「本の推薦」ラベルを作っておく（推薦の Issue に自動で付き、一覧で絞り込める）

### 分野ごとの質問票を作る（Markdown）

「この分野にはどの本が必要か」をまとめて聞くための質問票を、今のデータから作れます。
載っている本ごとの必要度（◎ ○ × ?）・本がないスキル・追加したい本を、分野ごとに書き込む形です。

```
py tools/make_book_survey.py 質問票.md
```

本を追加・削除したら作り直します。答えを書いたファイルを Claude に渡せば、`books.yaml` に反映できます。

### 選書ボード（画面で選ぶ・claude.ai のアーティファクト）

質問票と同じことを、ボタンで行える画面が `book-selection.html` です（claude.ai のアーティファクトとして公開し、オーナーだけが保存できる）。
本ごとに ◎ ○ × ? を押し、足りない本は「＋ 本を追加する」から書き足します。答えはアーティファクトのデータベースに保存され、
「選書ボードの結果を反映して」と Claude に頼めば `books.yaml` に反映できます。
GitHub Pages には載せません（データベースは claude.ai の中でしか動かないため）。

### データの検査

YAML は**字下げ（スペース2つずつ）で階層を表します**。タブは使いません。直したら、検査スクリプトで矛盾がないか確かめます。

```
py tools/validate_data.py
```

「存在しない id を指している」「矢印が輪になっている（A→B→A）」などがあれば、原因が表示されます。
ページを開いたときも、問題があれば上部に赤い枠で表示されます。

## 5. GitHub Pages への公開手順

### 初回だけ行うこと

1. GitHub にリポジトリを作り、このフォルダの中身を push する（`main` ブランチ）
2. リポジトリの **Settings → Pages** を開く
3. **Build and deployment → Source** を **「GitHub Actions」** にする（「Deploy from a branch」ではない）
4. **Actions** タブで「Deploy to GitHub Pages」が動き、緑のチェックになるのを待つ（1〜2分）
5. Settings → Pages の上部、または Actions の実行結果に表示される URL を開く
   （形は `https://ユーザー名.github.io/リポジトリ名/`）

### 2回目以降

`main` ブランチに push（またはプルリクエストをマージ）するだけで、自動で検査 → 公開されます。

- 検査で問題が見つかると公開されず、Actions の画面に原因が表示されます
- プルリクエストを出した時点でも検査だけが動くので、マージ前に間違いに気づけます

## 6. 公開ページで守ること

GitHub Pages は**誰でも見られる公開ページ**です。

- 個人名・連絡先・内部の検討内容（打上げ枠・企業との調整など）は載せない
- esa の記事を載せるときは、リンク（URL）だけにする。本文は転記しない
